# 結論(要約)

| # | 機能 | 難易度(1-5) | 初学者目安時間(推測) | 就活映え |
|---|---|---|---|---|
| 1 | スケルタルアニメーション(スキニング) | **5**(最難) | 4〜8週(週5-10h) | 高(動きの実装力の証明として強い) |
| 2 | パーティクルシステム(CPU) | 2 | 数時間〜1週 | 中(見栄えは良いが技術的希少性は低い) |
| 2' | パーティクル(GPUインスタンシング) | 3 | 1〜2週 | 中〜高 |
| 3a | 地形(ハイトマップ) | 2〜3 | 1〜2週 | 低〜中(静止画で十分伝わる) |
| 3b | 水面(反射・屈折・Fresnel) | 4 | 2〜4週 | 高(動画前提の効果) |
| 3c | スカイボックス(単純キューブマップ) | 1〜2 | 数時間〜数日 | 低 |
| 3c' | 大気散乱(Rayleigh/Mie物理ベース) | 4 | 2〜3週 | 中(昼夜遷移の動画でのみ真価) |
| 4 | トゥーン(NdotL+背面法輪郭線) | 2 | 数日〜1週 | **高(日本市場では特に有効)** |
| 4' | トゥーン高度版(ポストエフェクト輪郭線・法線編集) | 4 | 2〜3週 | 高 |

**glTF vs FBX**: glTFを推奨(検証済み)。FBXはAutodeskの非公開プロプライエタリ形式で、公式仕様書が存在せず、Blender開発チームが独自に仕様をリバースエンジニアリングして公開しているレベル。自作パーサー(Assimp不使用というプロジェクト方針)で読むのはFBXでは非現実的。glTFはJSON+バイナリのオープン仕様で、Assimpなしで一から書いたスキニング実装例(GitHub)も存在する。

**動画 vs 静止画**: スケルタルアニメーション・パーティクル・水面・大気散乱(昼夜遷移)は**動画でしか価値が伝わらない**(状況証拠+論理的帰結)。地形・スカイボックス単体・輪郭線の見た目自体は静止画でも十分。ただし採用担当者向け一般論として、プログラマー職ポートフォリオは静止画より短い動画(60〜90秒、字幕つき)が明確に推奨されている(検証済み)。

## 1. スケルタルアニメーション(スキニング)

| 項目 | 内容 |
|---|---|
| 難易度 | 5(自作レンダラーの中で最難関) |
| 前提 | Mat4は既存だが**クォータニオン(Quat)クラスが未整備**(Phase1のVec3/Mat4だけでは不足)。ボーン階層・行列パレットスキニングの理解も必要 |
| 目安時間 | 推測: 4〜8週(週5-10h)。既存機能より1桁重い |
| 就活映え | 高(3Dキャラゲーム業界で「動くキャラ」を自作で見せられる例は少数派) |

- LearnOpenGLのSkeletal Animation章は公式に「先にModel Loading章を終えてから」と前提を明示し、`aiScene`/`aiAnimation`/`aiNodeAnim`/`aiBone`など**Assimpに強く依存**した設計。`Vertex`(ボーンデータ拡張)/`Bone`/`Animation`/`Animator`という複数クラスの相互連携が必要で、初心者向けとは言えない中〜上級コンテンツ。チュートリアル内で使用されているのはglTFでもFBXでもなく**DAE(Collada)**形式(検証済み、https://learnopengl.com/Guest-Articles/2020/Skeletal-Animation )。
- Khronosフォーラムでは学習者が「何も理解できない、もっと簡単な方法はないのか」と投稿するほど躓きやすい題材(https://community.khronos.org/t/skeletal-animations-i-dont-understand-anything-isnt-there-a-simpler-way-on-how-to-do-this/111677 )。
- 「スキニングは自明とは程遠い」「非自明なので早めに着手すべき」という大学課題の注意書きもあり(検証済み、Chicago大CS課題PDF)、初心者にとって重い題材であることは複数ソースで一致。
- **glTF vs FBX**: FBXはバイナリ仕様が非公開で、Blender開発チームが独自にリバースエンジニアリングした「非公式仕様」しか存在しない(https://code.blender.org/2013/08/fbx-binary-file-format-specification/ )。対してglTFはオープン仕様で、Assimpを使わずGLTF 2.0のPOSITION/JOINTS_0/WEIGHTS_0や逆バインド行列を自前実装した公開プロジェクトもある(https://github.com/Snehasis-Das/Skeletal_Animation_Engine )。JavaScript/Web分野でも「glTFの方が学習コストが低い」との評価あり(https://webgl2fundamentals.org/webgl/lessons/webgl-skinning.html )。→ Assimp不使用方針と整合するのは**glTF一択**。

## 2. パーティクルシステム(CPU/GPUインスタンシング)

| 項目 | 内容 |
|---|---|
| 難易度 | CPU版: 2 / GPUインスタンシング版: 3 |
| 前提 | 既存の描画パイプライン、`glBlendFunc`によるアルファブレンド、インスタンシングなら`glDrawArraysInstanced` |
| 目安時間 | CPU版は数時間〜1週間、インスタンシング版は1〜2週間(推測) |
| 就活映え | 中(見栄えは良いが実装の技術的難度は低いため差別化力は限定的) |

- 基本的なCPUパーティクルは「非常に簡単で数時間で実装可能」との記述あり(https://gtstu.com/how-long-does-it-take-to-make-an-indie-game/ 系の記事群、およびitch.io devlog)。
- インスタンシングは「性能と実装容易性のバランスが良い」手法とされ、毎フレーム更新するのは小さなバッファ(パーティクル中心座標)のみで済み帯域が4倍改善するとの解説あり(http://www.opengl-tutorial.org/intermediate-tutorials/billboards-particles/particles-instancing/ )。
- GPU側完結の実装(Transform Feedback/コンピュートシェーダ)は視覚的フィードバックが得にくくデバッグが難しいため、燃え尽きの報告例あり(GameDev.net, itch.io投稿)。→ コスパ最優先ならCPU+インスタンシングが最も費用対効果が高い。

## 3. 地形(ハイトマップ)・水面・スカイボックス/大気散乱

### 3a. 地形(ハイトマップ)
- 基本メッシュ生成(`(rows-1)*(cols-1)`個のクアッド)は「非常に簡単」。難しいのは頂点法線計算(隣接三角形からの平均法線)で、これが最大の山場。マルチテクスチャレイヤーの追加はハイトマップ基礎ができていれば大きく難しくならない(https://www.mbsoftworks.sk/tutorials/opengl4/016-heightmap-pt1-random-terrain/ ほか)。
- Perlin/procedural生成は「地形をアーティストなしで作れる」利点があるが、ノイズアルゴリズム自体の学習コストが追加される。**初心者は既製ハイトマップ画像(グレースケールPNG)を読み込む方式の方が近道**(状況証拠、複数チュートリアル比較より)。

### 3b. 水面(反射・屈折・Fresnel)
- 反射・屈折それぞれをFBOにレンダリングし、Fresnel項でブレンドする構成が標準的。Fresnel項の計算自体は「視線ベクトルと法線の内積」で求まるが、**反射/屈折2パス+クリッピング平面+DuDv歪みマップ+法線マップ+スペキュラという多段構成が必要**で、中〜上級内容と位置づけられる(https://trederia.blogspot.com/2014/09/water-in-opengl-and-gles-20-part-4.html 、Khronosフォーラム)。
- 定番のThinMatrix水チュートリアルは複数回に分割された連載形式(Introduction/Projective Texture Mapping/Normal Maps/Fresnel Effectなど個別回が確認できた、https://thinmatrix.tumblr.com/post/116745646572/opengl-water-tutorial-1-introduction 等)で、1〜2回で終わる軽量な題材ではないことが裏付けられる。
- **Phase1のシャドウマッピング(ストレッチゴール)でFBO+深度テクスチャを習得済みなら、水面の反射/屈折パスは技術的に地続き**(推論、状況証拠から導出)。シャドウマッピングを達成済みなら心理的ハードルは下がる。

### 3c. スカイボックス / 大気散乱
- 単純なキューブマップスカイボックス(6枚の画像を貼るだけ)はLearnOpenGLの標準章で扱われる基礎レベルの内容(https://learnopengl.com/Advanced-OpenGL/Cubemaps )。
- 一方、Rayleigh/Mie散乱を物理ベースで再現する大気散乱は、レイマーチング+散乱積分+オゾン吸収まで踏み込むと明確に上級(https://blog.maximeheckel.com/posts/on-rendering-the-sky-sunsets-and-planets/ )。ただし精度を求めなければ「比較的安価に計算できる」との評価もあり(vterrain.org)、簡易近似版なら難易度を抑えられる。

## 4. トゥーンレンダリング/NPR(セルシェーディング+輪郭線)

| 項目 | 内容 |
|---|---|
| 難易度 | 基本(NdotL量子化+背面法輪郭線): 2 / 高度版(ポストプロセス輪郭線・法線編集): 4 |
| 前提 | 既存のPhongシェーダー(ambient/diffuse/specular)をNdotLベースの階調表現に置き換えるだけで着手可能 |
| 目安時間 | 基本版: 数日〜1週間、高度版: 2〜3週(推測) |
| 就活映え | **高、特に日本市場で有効** |

**実装難易度の根拠**:
- 輪郭線描画の最も簡単で一般的な手法(背面法/法線押し出し=モデルを法線方向に拡大して裏面カリングで2回描画)は「実装は非常に簡単」と明記(https://w.atwiki.jp/opengl/pages/317.html )。ただしハードエッジモデルで破綻しやすい弱点あり。
- ポストプロセス型(深度/法線バッファのエッジ検出)は画面全体で均一な太さ・負荷になる利点があるが、部位ごとの線の太さ・色調整が難しく3DCGソフト上でのプレビューがしにくいという欠点あり(https://light11.hatenadiary.com/entry/2018/05/13/183314 、blog.syn-sophia.co.jp)。

**日本のゲーム業界での需要(検証済み・複数事例)**:
- **カプコン「モンスターハンターストーリーズ3」**: CEDEC2026講演(2026年8月、直近)で「劇場版風」のアニメ調表現を目標に掲げ、NdotLベースの2階調シェーディング(グラデーションでなく境界のはっきりした表現)、フレア・アウトライン・リムライトなどのポストエフェクトを組み合わせていることが報告された。同記事は「セルルックを用いた国産ゲーム制作は、海外での増加傾向に対し国内では貴重な取り組み」と位置づけており、**日本国内では相対的に希少な技術領域**であることを示唆(https://www.famitsu.com/article/202608/83946 )。実装は初期にフォワードライティングで検証し、後にディファードライティングへ移行するという負荷対策も行われた。
- **Cygames「グランブルーファンタジー:Relink」**: 2Dイラストを3DCGで再現するために技術者が総力を挙げた開発事例として業界誌で特集(https://cgworld.jp/special-feature/202403-relink1.html )。CygamesはCEDEC講演を積極的に公開しており技術力アピールに力を入れている企業。
- **アークシステムワークス「GUILTY GEAR Strive/Xrd」**: 手描きアニメに近づけるため頂点法線を手動編集し影の落ち方を意図的に制御する高難度技術で知られる。アートディレクターは「リアル路線ではなくセルシェーディングのアニメ調路線でなら戦えると感じた」と明言しており、差別化戦略としてのNPR採用が明確(状況証拠、moonjump.com記事・GDC資料PDF)。
- **参考(海外/中国だが業界影響大): 原神(miHoYo)**: セルシェーディング+アウトライン+リムライト+カスタムトーンマッパーなど多機能シェーダーで、キャラクターをフォワード、シーンをディファードと分けてレンダリングする設計。世界的ヒットにより「アニメ調3D表現」の商業的成功例として業界の意識を大きく変えた(https://adrianmendez.artstation.com/projects/wJZ4Gg 、80.lv記事)。

**ポートフォリオ評価としての位置づけ**: 日本の新卒エンジニア就活情報サイトでも、自作トゥーンシェーダーはポートフォリオ素材として有効とされ、「単なる実装だけでなく背景理論をどう実装に落とし込んだか」を説明できることが評価点になると明記(https://paiza.jp/student/advice/student_portfolio 、https://www.geekly.co.jp/column/cat-position/game-graphics-engineer/ )。

## 5. 動画映えするか(静止画 vs 動画)

| 機能 | 動画の必要性 | 理由 |
|---|---|---|
| スケルタルアニメーション | **必須** | 静止画は1フレーム(Tポーズ等)しか見せられず、ボーン補間・ブレンドという本質が伝わらない |
| パーティクル | **必須に近い** | 炎・煙・火花は動きそのものが情報量。静止画では平板に見える |
| 水面 | 高 | 波のうねり・反射屈折の変化・Fresnelの視野角依存性は動きの中でのみ説得力を持つ |
| 大気散乱(昼夜遷移) | 高 | 太陽移動に伴う空の色変化という時間軸現象。単一スカイボックスの静止画は通常のスカイボックスと区別がつきにくい |
| 地形 | 低〜中 | 幾何形状の見栄えは静止画でも十分。カメラフライスルー動画があれば加点程度 |
| スカイボックス(単体) | 低 | 静止画で完結する情報量 |
| トゥーン/輪郭線 | 中 | シェーディングと輪郭線自体は静止画でも伝わるが、キャラクターが動いた時に輪郭線が破綻しないかは動画でしか検証・アピールできない |

**一般的なポートフォリオ動画の作法(検証済み)**: プログラマー職では静止画よりも動画が明確に推奨される。採用担当者は1つのポートフォリオに10〜30秒しか目を通さないため、60〜90秒程度に編集し、冒頭5〜10秒に最も見栄えする部分を配置、字幕で「何を自作したか」を明示するのが効果的とされる(https://generalistprogrammer.com/tutorials/game-developer-portfolio-and-resume-guide 、https://lindenreidblog.com/2019/02/24/game-dev-portfolio-guide/ 、GameDev.netフォーラム )。無音・無字幕のクリップは何がすごいのか採用側が推測する負担を強いるため評価を下げる、という指摘は特に重要。

## 確信度と限界

- **検証済み(高確信度)**: glTFがFBXよりも自作パーサー向きであること/LearnOpenGLのSkeletal Animation章がAssimp依存で中上級者向けであること/カプコン・Cygames・アークシステムワークスが日本市場でNPRに注力している実例/ポートフォリオは動画が静止画より評価されるという一般論。いずれも複数の一次資料・業界記事で裏付け。
- **状況証拠(中確信度)**: 各機能の「初心者にとっての相対難易度順位」(スケルタルアニメーション>水面/大気散乱>パーティクルGPU版>地形/トゥーン基本版>スカイボックス基本版)。個別の難易度に関する記述はあるが、同一条件下で横並び比較したベンチマークではないため、相対順位は複数ソースの記述を筆者が統合した推論。
- **推測(要注意)**: 「初学者の目安時間」の具体的な週数はいずれもWeb上に直接の実測データが見つからず、ユーザーのPhase1実績(週5〜10h、4ヶ月でOBJパーサー+Phongライティング+シャドウマッピングを達成)を基準にした相対推定。実際の所要時間は個人差・学習効率で大きく変動しうる。
- **覆り得る条件**: モンスターハンターストーリーズ3の「国内では貴重」という位置づけは1件の記事(CEDEC2026講演の二次報告)に基づくため、他の日本語ゲーム会社の類似事例(例: 原神以降に追随する日本発タイトル)が増えていれば「希少性」の評価は変わりうる。また、ThinMatrix水チュートリアルの総話数は検索では確認できず、断片的なエピソードタイトルからの状況証拠に留まる。
